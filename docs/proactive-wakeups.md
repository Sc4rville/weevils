# Event wake-ups for weevboss

Event wake-ups belong to the canonical product, with no personal configuration or new runtime dependency. They run only with stateless boss turns on the main machine. Integration and a verified safe restart are separate from implementing and testing this branch; the live service was not restarted.

## Behavior

The durable inbox observes completed turns, confirmed human questions and interruptions, plus open/dispatched requests without actual progress for 24 hours. First discovery establishes a baseline; historical questions and cuts are not revived on the following scan. New observations use source activity/notice identities, and superseded or answered events leave the inbox. Stale events retain their request ID, source and actual recorded author. The events are observations, never new user requests, authorization or automation runs.

A batch waits for three quiet minutes, with a ten-minute ceiling. Each batch contains up to 24 current events; overflow remains pending. At most eight proactive triage evaluations and eight proactive launches occur per UTC day, including across restart. Cheap Haiku triage rejects routine batches; a useful batch receives Sonnet at low effort with at most eight CLI turns. This limit does not promise a dollar ceiling. A failed pre-launch triage waits for another quiet period, still under the evaluation cap. Launch identity is saved before spawning; uncertain launches and resumptions are not blindly repeated.

User messages take priority. Waiting events join the user's existing turn as hidden context, without another request capture or changing its selected model/effort. A user arriving during preparation takes the next slot. Pause and Standby (`pause`, `veille`), disabled wake-ups, provider holds and an active boss prevent event-only turns. A saved relay episode is checked explicitly, including a near-limit episode that ordinary interactive routing may still allow.

`weevils config set WEEVILS_BOSS_PROACTIVE 0` disables wake-ups immediately. `weevils config set WEEVILS_SPEED_MODE pause` supplies a production-readable mode gate until the app's speed-mode source is connected; the source installed by `setSpeedModeSource` takes precedence. The app does not yet have Pause/Standby controls. These two non-secret settings persist through the existing config route without restarting the service.

Session reports remain provisional: the ledger does not close a dispatched request merely because its cheap judge returns “done.” Instructions in both languages require inspecting the working result and recording what was checked before closure. Follow-ups must stay attached to the original request and reuse compatible ordinary project work through the canonical route. Scheduler-owned runs stay with their scheduler/router and restrictions. Repository adoption is never evidence of request origin or execution.

For proactive resumption, `weevils send <id> "<authorized continuation and job-inspection instructions>" --safe-resume` uses the normal delivery route, source-session resolution and signed actual author. The guard refuses live or queued work, tracked surviving jobs, same-folder active/question-blocked work, missing/read-only source, quota/auth/dirty interruptions, relay ownership, and scheduler-owned current runs and stops belonging to recorded runs. Later human work in the same session is not permanently classified as automated. It reserves the interruption notice before delivery. It does not spend money, provision machines or bypass a refusal. Workers must inspect independent surviving jobs before acting. Ordinary manual sends/resumes keep their existing behavior.

Existing session cards and push notifications carry the underlying notices. Wake-up instructions forbid repeating them and allow at most one useful outcome or evidenced result card. A standalone final silence-marker line suppresses the entire assistant outcome, including explanatory prose a model may prepend. This applies to visible boss messages and cached/rebuilt history; user words and raw transcripts are preserved. Unreadable event state disables wake-ups rather than resetting deduplication or stopping the app.

## Validation, 2026-11-17

The implementation has dedicated tests for persisted event replay and baselines, batching/deadlines, caps and UTC rollover, live disable/mode gates, cheap silence/failure, user priority during triage and preparation, uncertain launch/resumption suppression, independent verification, canonical sender provenance, scheduler restrictions, and silence filtering in the thread and cached history. The final check count is recorded in the accompanying review receipt.

An isolated Docker copy was built and started through `scripts/test-copy.sh`, with separate data, ports and terminal socket. Desktop Chromium (1440 × 1000) and phone-width Chromium (390 × 844) signed in, rendered without page errors or horizontal overflow, and displayed no silent-outcome text. The server was restarted only inside this copy.

One real subscription-backed Sonnet 5.5 turn evaluated a controlled stale-request fixture and correctly chose silence because no real user result existed. That exposed two issues which were then corrected: ordinary interactive routing permits a near-limit Claude episode, so proactive routing now checks the episode separately; the model appended the silence marker to explanatory prose, so that whole outcome is now hidden. Raw output remains in private test evidence. The corrected restart test retained a due fixture event without increasing triage/launch counts under the saved quota hold. No quota setting was weakened to produce another run.

A useful positive message from the real model remains unverified; the positive path is covered with controlled model doubles. A real iPhone, Safari/WebKit, Apple push delivery, live follow-through and live activation were not tested. The remaining real-model example must wait for actual provider availability, rather than overriding its hold. No live session or existing job was stopped, restarted or duplicated; the pod listing was empty, and no GPU was provisioned.

## Measured cost assumptions

The prepared fresh-profile view measured approximately 9,795 stable tokens plus 144 event-context tokens; this excludes the CLI's own system/tool overhead. The real silent turn used 2 uncached input tokens, 13,431 one-hour cache-write tokens, 16,809 cache-hit tokens and 49 output tokens. The cheap triage ledger recorded 4,541 total tokens for one call. These are measurements of this short test, not a forecast of useful verification work.

Using [Anthropic's published prices](https://platform.claude.com/docs/en/about-claude/pricing), Sonnet 5.5 input/output are $2/$10 per million tokens, one-hour writes $4, and cache hits $0.10; short-context Haiku 5.5 input/output are $0.10/$0.50. The measured silent Sonnet turn is about $0.056 API-equivalent. Eight similar short reviews are about $0.45 with that cache pattern, or $0.98 if their full 30,242-token input is written cold for an hour each time, including less than one cent for comparable triage. Assuming 1,000 output tokens per review instead of 49 makes that approximately $0.53–$1.06/day. Tool rounds, growing history, summaries and any authorized worker follow-through add consumption; eight wake-ups is not a hard money budget.

The code uses the existing Claude Code login and quota, with no new paid API account or GPU. These dollar figures are API-equivalent comparisons, not an additional subscription invoice. Price and model aliases can change; remeasure actual useful reviews after quota recovery before claiming a daily production cost.
